# 装修效果展示网站 · 方案设计

版本：v0.2｜日期：2026-10-12｜状态：已按本方案进入开发，M1（数据与修改入口）、M2（平面户型图）已完成，见[验收清单](03-验收清单.md)｜依据：[需求澄清 v0.8](01-需求澄清.md)

> 一句话方案：一份设计数据（JSON）放在浏览器里，所有修改，无论来自鼠标、参数面板还是 AI，都写成“修改指令”，交给同一个引擎检查和执行；平面图和 3D 只负责把这份数据画出来。

## 0. 怎么读这份文档

本文回答“怎么做”：数据怎么存、模块怎么拆、AI 怎么接、程序怎么在另一台电脑跑起来。需求里已经说清的“做什么”不再重复，只用功能编号（如 TRY-03）引用。

文中结论分三种：

- **已核实**：本机实测或查阅官方资料得到的事实，第 19 节列出命令、日期和结果。
- **设计决定**：为实现需求做出的选择，开发中可以调整，调整时记入变更记录。
- **待验证**：只能写完代码后才能证明的事，例如性能和各厂商模型的实际表现，安排在对应里程碑里测。

需求中的“草案默认”在这里被具体化。凡是与需求原文有出入或需求没写到的地方，集中列在第 17 节，不悄悄改需求。

## 1. 设计原则

| 原则 | 具体做法 | 对应需求 |
|---|---|---|
| 一份数据，多种画法 | 只有一个“当前设计”对象；平面图、3D、参数面板、AI 上下文都从它读，没有各自的副本 | 第 3.1、10 节，VIEW-02 |
| 一个修改入口 | 任何修改都先变成“修改指令”，由引擎检查后整批执行或整批拒绝 | EDIT-02、EDIT-06、AI-03、AI-06 |
| 显示和数据分开 | 剖面、单间视图、展示基座、相机只影响画面，不写入房屋结构 | VIEW-03、8.1、8.3 |
| 存的是输入，算的是结果 | 只保存用户能编辑的值（房间矩形、墙厚等）；墙段、室内净尺寸、房屋外轮廓每次由程序算出，避免两处数据对不上 | 第 4.1、5.1 节 |
| 核心逻辑不依赖界面 | 数据、几何、引擎三层是纯 TypeScript，不引用 React、Three.js 或浏览器接口，可以单独测试 | 第 10 节 |
| 只信实际结果 | AI 只“提议”；成功、失败、已应用与否一律以引擎返回为准，界面和 AI 都不能自己宣称完成 | AI-05 |

### 2.2 依赖规则

- 箭头只能向下：界面层可以用状态层和纯逻辑层，纯逻辑层不能反过来引用界面。
- `model`、`geometry`、`engine`、`catalog` 四个目录禁止引用 `react`、`three` 和任何浏览器对象（`window`、`document`、`indexedDB`）。用一个自动测试扫描这些目录的 `import` 语句来保证，不额外引入代码检查工具。
- `ai` 只通过“提交修改指令”影响设计，不能直接改状态；增加一家厂商只新增一个适配文件（MODEL-05）。
- `plan` 和 `scene3d` 互不引用，各自只读状态层，所以改 3D 不会碰坏平面图。

## 5. 坐标与尺寸口径

所有模块共用以下定义，AI 提示词里原样写入，保证“向左 20 厘米”在手动和 AI 中意思相同（FURN-04）。

| 项目 | 定义 |
|---|---|
| 单位 | 毫米，整数。界面可显示为米（4000 → 4.00 m），存储始终是毫米 |
| 平面坐标 | 原点在画布左上；x 向右为正，y 向下为正。“左”= x 减小，“右”= x 增大，“上”= y 减小，“下”= y 增大 |
| 房间矩形 | `x, y` 是左上角，`length` 沿 x（左右），`width` 沿 y（上下）；四条边就是四面墙的中心线（轴线尺寸，需求 4.1 已确定） |
| 室内净尺寸 | 净长 = 长 − 左墙厚/2 − 右墙厚/2；净宽同理。某条边整段开放时，该边扣 0。一条边上有多段不同厚度的墙时，取最厚的一段，宁可算小 |
| 墙参考端 | 上、下边从左端量起；左、右边从上端量起。门窗的“位置”就是洞口起点到参考端的距离 |
| 家具位置 | `cx, cy` 是家具底面中心相对所属房间左上角（轴线）的距离；`elevation` 是离地高度 |
| 家具朝向 | `rotation` 单位为度，0° 表示正面朝下（+y），顺时针为正，取值 0–359 |
| 3D 换算 | 3D 中 1 个单位 = 1 米；平面 x → 3D X，平面 y → 3D Z，高度 → 3D Y；地面在 Y = 0 |

例：客厅 `x=0, y=0, length=5000, width=4000`，四周外墙厚 240，则室内净尺寸为 4760 × 3760 mm。沙发 `cx=2500, cy=3200, rotation=180` 表示沙发中心在客厅中部偏下，正面朝上（朝 −y）。

## 6. 数据模型

### 6.1 设计文件的整体结构

```ts
interface Design {
  schemaVersion: 1;            // 数据格式版本，升级时靠它做迁移
  revision: number;            // 每次成功修改 +1，用来判断“试看是否过期”
  meta: { name: string; createdAt: string; updatedAt: string };
  defaults: { exteriorThickness: 240; interiorThickness: 120; wallHeight: 2800 }; // 可改
  rooms: Room[];
  walls: Record<WallId, WallOverride>;   // 只存用户改过的墙属性
  openings: Opening[];                   // 门和窗
  furniture: Furniture[];
  style: Style;                          // 室内风格
  display: Display;                      // 展示基座与单间展台
}
```

不存进设计的东西：墙段几何、室内净尺寸、房屋外轮廓（都是派生数据）；当前页面、模式、选中对象（属于界面状态）；聊天记录和 API Key（第 9.7 节）。

### 6.2 房间

```ts
interface Room {
  id: string;                // 如 "r_3f9a1c2e"，创建后不变
  name: string;              // 客厅
  usage: 'living' | 'bedroom' | 'kitchen' | 'bathroom' | 'balcony' | 'other';
  x: number; y: number;      // 轴线左上角
  length: number; width: number;
  planColor: string;         // 平面识别色，#RRGGBB
  floor?: { material?: FloorMaterialId; color?: string };     // 不填则跟随风格
  wallColors?: Partial<Record<Side, string>>;                 // 本房间这一侧的墙面颜色
}
type Side = 'top' | 'right' | 'bottom' | 'left';
```

没有旋转字段（Q-03 已确定）。墙面颜色挂在房间上，天然实现“共用墙两侧颜色不同”（WALL-03）：客厅的右边和卧室的左边是同一面墙的两侧，各存各的颜色。

### 6.3 墙：由房间推导

墙不单独绘制，也不单独存位置（WALL-01）。程序按以下步骤从房间算出墙段：

1. 收集所有房间的边，按所在直线分组，例如所有 y = 4000 的水平边归为一组。
2. 在同一直线上，把所有边的端点作为切分点，切成若干小区间。
3. 每个小区间看两侧各有没有房间：只有一侧有房间，就是**外墙**；两侧都有，就是**共用墙**。由于房间不允许重叠，每侧最多一个房间。
4. 把相邻且归属相同的小区间合并，得到最终的墙段。

墙段的编号由归属决定，只要房间关系不变，编号就稳定：

| 墙段类型 | 编号格式 | 例子 |
|---|---|---|
| 外墙 | `ext:{房间id}:{边}` | `ext:r_a1:top`：客厅上边不与其他房间相邻的部分 |
| 共用墙 | `shared:{较小id}\|{较大id}` | `shared:r_a1\|r_b2`：客厅与卧室之间的墙 |

两个横平竖直的矩形最多只共用一段墙，所以“房间对”能唯一确定一面共用墙。一条边若一部分与卧室相邻、其余部分朝外，就会得到一段共用墙和一到两段外墙，外墙部分共用 `ext:` 编号与属性。

用户改过的墙属性存在 `walls` 里，没改过的用默认值：

```ts
interface WallOverride { thickness?: number; height?: number; open?: boolean }
```

- **厚度**：沿中心线向两侧各长一半；改厚度不移动房间（需求 4.1 已确定），只改变室内净尺寸。默认外墙 240、共用墙 120。
- **整段开放**（WALL-04）：`open: true` 时这一段不建墙，3D 中两侧地面直接连上。L 形空间就是两个房间的共用墙设为开放。
- **关系变化**：房间移动后不再相邻，原 `shared:` 记录失去对应的墙。引擎在同一次修改中删除这条记录，并在差异列表里写明“客厅与卧室不再相邻，原共用墙设置已移除”；以后再相邻时使用默认值。

### 6.4 门窗

```ts
interface Opening {
  id: string;
  kind: 'door' | 'window';
  hostRoomId: string; side: Side;  // 挂在哪个房间的哪条边上
  offset: number;                  // 洞口起点到参考端的距离
  width: number; height: number;
  sill: number;                    // 洞口底部离地高度；门恒为 0
  // 门
  use?: 'entry' | 'interior';                  // 用途：入户门 / 室内门
  openMode?: 'swing' | 'sliding' | 'none';     // 开启方式：平开 / 移门 / 无门扇
  hinge?: 'start' | 'end';                     // 平开门铰链在靠参考端一侧还是另一侧
  swingInto?: 'host' | 'other';                // 平开门开向本房间还是另一侧
  slideTo?: 'start' | 'end';                   // 移门滑向哪端
  // 窗
  windowType?: 'floor' | 'standard';           // 落地窗 / 普通窗
  colors?: { leaf?: string; frame?: string };  // 门扇、门框/窗框颜色
}
```

门窗挂在“房间的边”上，而不是挂在墙段编号上。好处是房间移动时，门窗跟着本房间走，位置不需要重新计算；共用墙上的门由创建它的房间“持有”，参数面板同时显示两侧房间名称。

门窗检查（错误，不能提交）：

- 洞口必须完整落在**一段已建墙**内：不能伸出墙端，不能跨过外墙与共用墙的分界，不能放在开放边上。
- 同一条直线上，不论哪个房间持有，洞口之间不能重叠。
- `sill + height` 不能超过所在墙的高度；改墙高时同样检查已有门窗（WALL-02）。
- 入户门只能在外墙上（DOOR-01）。
- 不适用的字段不能出现：例如无门扇的门不能有 `hinge`，窗不能有 `use`。这样面板也不会显示无意义的选项（DOOR-04、DOOR-05）。

室内门放在外墙上只给提示，不阻止。

### 6.5 家具

```ts
interface Furniture {
  id: string;
  templateId: string;          // 如 "sofa.3seat"
  name: string;                // 默认取模板名，可改
  roomId: string;
  cx: number; cy: number;      // 相对房间轴线左上角
  rotation: number;            // 0–359
  l: number; w: number; h: number;   // 长（沿家具左右）、宽（前后进深）、高
  elevation: number;           // 离地高度，默认 0
  appearance?: Record<PartId, { color?: string; material?: MaterialId }>; // 只存改过的部件
}
```

位置检查：

- **错误**：家具占地（按旋转后的四个角计算）超出所属房间的室内净范围，就是“穿墙或放到房外”，不能提交。开放边不扣墙厚，但家具仍须留在自己房间内，不能横跨到相邻房间（第 17 节第 5 条）。
- **错误**：尺寸、材质超出模板允许的范围，提示“该家具不支持……”，而不是显示成功（需求第 6 节）。
- **提示**：家具与家具占地重叠只提示；模板标记为“可叠放”的（如地毯）不提示。
- 移动家具到另一个房间：修改 `roomId` 并给出新坐标，引擎按新房间检查（需求 4.2）。

### 6.6 家具模板与材质

家具和材质都由程序生成，不读取外部模型文件：

- 每个模板写清楚：编号、版本、类别、中文名、默认尺寸、长宽高允许范围、部件列表（每个部件的角色和允许材质）、是否可叠放、平面图符号、3D 造型函数。
- 3D 造型用圆角方块、圆柱等基本体拼出，符合微缩模型的“适度圆润”（第 8 节）。造型函数放在 `scene3d`，模板的数据部分放在 `catalog`，后者保持纯逻辑。
- 材质用画布实时生成木纹、布纹、地砖等纹理，使用固定随机种子，在另一台电脑生成完全相同的效果（SAVE-05）。

### 6.9 编号与格式版本

- 对象编号用浏览器自带的 `crypto.randomUUID()` 生成，取前 8 位并加类型前缀（`r_` 房间、`o_` 门窗、`f_` 家具），检查不重复。编号较短，AI 上下文更省字数。
- `schemaVersion` 每次改变数据格式时加 1，并写一个从旧版转换到新版的迁移函数；导入旧文件时依次迁移。

## 7. 统一修改引擎

### 7.1 修改指令

所有修改都写成指令列表，一批指令就是一次修改。

| 指令 | 作用 | 主要参数 |
|---|---|---|
| `room.add` / `room.update` / `room.remove` | 增改删房间 | 位置、长宽、名称、用途、颜色、地面、墙面颜色 |
| `wall.update` | 改墙厚、墙高、是否开放 | `wallId`（第 6.3 节的编号） |
| `opening.add` / `opening.update` / `opening.remove` | 增改删门窗 | 持有房间、边、位置、尺寸、门窗类型字段 |
| `furniture.add` / `furniture.update` / `furniture.remove` | 增改删家具 | 模板、房间、位置、朝向、尺寸、部件外观 |
| `style.update` / `style.applyPreset` | 改风格参数 / 套用预设 | 调色板、地面、灯光；预设编号、是否覆盖 |
| `display.update` | 改基座和展台参数 | 边距、高度、颜色等 |
| `design.clear` | 清空设计 | 无 |

两个细节帮助 AI 少算错：

- `update` 同时支持 `set`（设为某值）和 `add`（在原值上加减）。“沙发左移 20 厘米”写成 `{op:'furniture.update', id:'f_1', add:{cx:-200}}`，不需要模型自己算出新坐标。
- 同一批中新增的对象可以先用临时编号 `new:xxx` 引用，例如先加房间、再在这个房间里加门。执行时替换成正式编号。

整个设计的替换（导入、恢复历史版本）不走指令，而由状态层直接整份替换；它同样经过完整检查，并记一步撤销（第 9 节）。

### 7.2 执行流程

```text
指令列表
  → ① 格式检查：Zod 严格模式，未知指令、未知字段、错误类型一律拒绝（AI-04）
  → ② 解析引用：对象是否存在，临时编号替换
  → ③ 在副本上执行：Immer 草稿，原设计不受影响
  → ④ 重新推导：墙段、净尺寸、相邻关系，清理失效的共用墙记录
  → ⑤ 整体检查：对结果做一次全量检查，得到错误与提示
  → 结果 { ok, next, changes, errors, warnings }
```

- 有任何错误，`ok` 为假，`next` 不被采用，原设计不变（EDIT-06）。
- `changes` 是差异列表：每一项写明对象、字段、旧值、新值，界面和 AI 都用它来展示“改了什么”（第 7.1 节第 3 步）。
- 同一个函数既用于“正式提交”，也用于“试看”和“拖动中的实时检查”，所以三者的规则永远一致（EDIT-02）。

### 7.3 检查规则与错误信息

每条错误都带：错误码、对象、字段、中文原因、修改建议。例如：

> 门「卧室门」放不下：它右端距墙端还差 150 mm。可以把位置减小到 2350 mm 以内，或把门宽改为 750 mm 以下。

主要规则与取值范围（设计决定，可调）：

| 对象 | 规则 | 级别 |
|---|---|---|
| 房间 | 长、宽 500–30000；两房间重叠面积大于 0（共边不算） | 错误 |
| 墙 | 厚度 50–500（大于 0，WALL-02）；高度 2000–4500，且不低于墙上门窗的顶部 | 错误 |
| 门窗 | 第 6.4 节各项；门宽 500–3000，窗宽 300–6000 | 错误 |
| 门窗 | 室内门在外墙上 | 提示 |
| 家具 | 超出室内净范围；尺寸或材质超出模板允许范围 | 错误 |
| 家具 | 与其他家具重叠（可叠放模板除外） | 提示 |
| 风格 | 颜色必须是 #RRGGBB；色温、亮度在允许范围内 | 错误 |

### 7.4 撤销与重做

- 撤销栈保存修改前后的整份设计快照。Immer 只复制改动部分，其余部分共用，所以存 100 步也很省内存。上限 100 步，超出丢弃最早的。
- 记一步的单位：一次参数提交、一次完整拖动（松手时）、一次应用的试看方案、一次恢复版本、一次导入替换（EDIT-03）。连续按方向键微调家具，0.5 秒内的多次合并为一步。
- 撤销栈只在内存中，刷新后清空（需求第 9 节）。
- 试看期间仍可撤销当前设计上的手动修改，试看会随之重新计算（第 8.3 节）。

### 8.1 界面状态

### 8.3 试看的应用与过期

试看记住它基于哪个版本号（`baseRevision`）和哪些指令（`ops`），而不只是记住一份结果：

1. **当前设计变了**（用户在试看期间手动修改或撤销）：把同一组指令在新的当前设计上重新执行一遍。
2. **冲突判断**：如果试看要改的对象字段，在这段时间里被手动改过，就判为冲突。试看标记为“已过期”，“应用”按钮不可用，提示“客厅在试看期间被手动修改过，请让 AI 重新生成”，并提供“重新生成”按钮（AI-07、TRY-06）。
3. **重新执行后不再合法**：同样标记过期，并显示具体原因。
4. **应用**：如果在预览模式，先切到编辑模式（TRY-07）；然后自动保存一个历史版本（VER-02），再写入当前设计，记一步撤销，触发自动保存。自动版本保存失败时弹出提示，让用户选择继续还是取消。
5. **放弃**：清除叠加层，不留下任何记录（TRY-03）。
6. **刷新或关闭**：叠加层只在内存中，自然消失（TRY-04）。

## 9. 保存、历史版本与导入导出

### 9.1 本地存储结构

浏览器的 IndexedDB 中建一个数据库 `renovation-designer`：

| 存储区 | 内容 | 说明 |
|---|---|---|
| `current` | 当前设计 + 保存时间 | 只有一条记录；刷新后恢复的就是它 |
| `versions` | 历史版本：编号、名称、时间、手动或自动、触发原因、整份设计 | 按时间建索引 |
| `thumbs` | 版本缩略图（图片数据） | 与版本分开存，列表加载更快 |
| `prefs` | 界面偏好、模型服务设置（地址、模型名，不含密钥） | |

API Key 不进这个数据库（第 9.7 节）。

### 9.2 自动保存（SAVE-01、SAVE-02）

- 每次成功修改后等 1 秒再写入，连续修改只写最后一次。保存状态显示为“未保存 → 保存中 → 已保存”，失败时显示“保存失败”和原因，并提供“导出备份”按钮。
- 只写当前设计。试看和历史查看不会触发保存。
- 程序启动时调用 `navigator.storage.persist()`，请求浏览器不要在空间紧张时自动清理本站数据。浏览器可能拒绝，所以界面仍提醒定期导出（需求第 9 节）。

### 9.3 历史版本（VER-01～08）

- **手动版本**：点“保存为版本”，可填名称，不填按时间命名。
- **自动版本**：在应用试看、删除房间、清空设计、导入替换、恢复版本之前自动保存，并记录触发原因，例如“应用 AI 修改前”。
- **数量**：自动版本超过 20 个时删除最早的自动版本；手动版本不自动删除。
- **空间检查**：保存前用 `navigator.storage.estimate()` 查看用量，超过可用空间的 90% 时提示清理，不静默丢弃。
- **缩略图**：3D 可用时截取 3D 画面（宽 320 像素），否则把平面图转成图片。截图只截画布区域，不会截到设置面板。
- **查看与恢复**：查看时进入“历史查看”叠加层，只有“恢复此版本”和“退出查看”两个按钮；恢复走第 8.3 节第 4 步同样的流程，可撤销。

### 9.4 导出（SAVE-03、SAVE-07）

导出文件名：`设计名-20261011-1530.rdproj.zip`，内含：

| 文件 | 内容 |
|---|---|
| `manifest.json` | 文件格式标识、格式版本、`schemaVersion`、程序版本、导出时间；用到的家具模板编号与版本、材质编号 |
| `design.json` | 当前设计，不含试看、历史版本、撤销记录、聊天记录、API Key |
| `preview.png` | 一张预览图，导入时用来确认 |

家具和材质是程序内置的，只记编号和版本，不重复打包（SAVE-03）。

### 9.5 导入（SAVE-04）

1. 选择 zip 文件，读出 `manifest.json`，确认是本程序的项目包。
2. `schemaVersion` 比本程序支持的新：拒绝，提示“请先更新程序”。比本程序旧：依次迁移。
3. 用与引擎相同的规则完整检查设计；不合法时列出问题并拒绝导入。
4. 检查用到的家具模板：编号存在且本程序的模板版本不低于文件中记录的版本，才算齐全；缺失时列出缺失项并阻止导入，不替换成别的家具（需求第 9 节）。
5. 显示摘要：名称、房间数、家具数、导出时间、预览图，确认后才替换。
6. 替换前自动保存一个历史版本；替换算一步修改，可撤销。

### 9.6 程序怎么运行、怎么带到另一台电脑（SAVE-06）

浏览器的本地数据按“网址 + 端口”分开存放：同一台电脑上，换一个端口打开就像换了一个浏览器，看不到之前的设计。所以程序必须**固定一个网址**。

- **固定网址**：`http://127.0.0.1:5180`。`server/serve.mjs` 是一个不依赖任何第三方包、约 80 行的 Node 静态服务，只监听本机。用 `localhost:5180` 访问时自动跳转到 `127.0.0.1:5180`，保证始终是同一个网址。
- **端口被占用**：不自动换端口，提示“5180 端口已被占用：如果程序已在运行，直接打开 http://127.0.0.1:5180；否则请关闭占用该端口的程序”。
- **开发时**：用 `npm run dev` 启动的是另一个端口，数据与正式使用的数据分开，互不影响。
- **生成程序包**：`npm run package` 产出 `release/装修设计器-v版本号/`，内含打包后的网页、`serve.mjs`、`启动.command`（macOS）、`启动.bat`（Windows）和《使用说明.txt》。
- **运行环境**：使用程序包只需要电脑装有 Node.js 18 或更高版本，不需要联网安装依赖；开发和打包需要 Node.js 20.19 以上或 22.12 以上（Vite 8 的要求）。本机为 Node 23.11.0，满足要求。
- **换电脑的完整步骤**（写进使用说明）：旧电脑“导出项目包” → 把程序包文件夹和项目包拷到新电脑 → 双击启动 → 新电脑浏览器中“导入项目包”。历史版本不随行（VER-08）。
- **macOS 提示**：拷来的 `启动.command` 第一次运行可能被系统拦截为“来自身份不明的开发者”，需右键选择“打开”。使用说明写明这一步。

### 9.7 API Key 的处理

- 默认只放在内存里，关闭页面即消失。
- 勾选“记住密钥”后，存在本浏览器的 localStorage，按厂商分开；勾选时明确提示：“密钥未加密，保存在本机浏览器中，能使用这台电脑和浏览器的人或恶意扩展可能读到。”可随时一键清除。
- 密钥不进 IndexedDB 设计库，因此不会出现在自动保存、历史版本、导出包中（SAVE-07、VER-06）。
- 输入框使用密码类型；错误提示和调试日志中不输出请求头，`Authorization` 一律替换为 `***`；缩略图只截画布（需求第 9 节）。

## 10. AI 接入

### 10.1 接入方式：浏览器直连

**已核实**：DeepSeek、百炼、GLM、OpenAI 四家的对话接口都允许网页跨域调用，用 `127.0.0.1:5180` 与 `localhost:5180` 两种来源测试都通过；故意用错误密钥请求时，浏览器也能读到 401 错误内容。因此首版**不需要本地转发服务**，浏览器直接调用厂商接口。厂商以后若收紧跨域，按第 16 节的预案处理。

四家都提供与 OpenAI 相同格式的 `chat/completions` 接口和“工具调用”能力。程序用一套统一的请求格式，厂商差异放在各自的适配文件里（MODEL-05）。

| 厂商 | 默认服务地址（可改） | 模型名 | 已核实的差异 |
|---|---|---|---|
| DeepSeek（默认） | `https://api.deepseek.com` | 示例 `deepseek-flash`，可改为文档列出的其他模型 | 工具调用与 OpenAI 格式兼容 |
| 百炼 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 留空，提示到百炼控制台复制支持工具调用的模型名 | 新文档也给出按工作空间区分的地址，故地址必须可改；通义千问对“强制调用工具”支持不稳定 |
| GLM | `https://open.bigmodel.cn/api/paas/v4` | 示例 `glm-5.3` | `tool_choice` 只支持 `auto`；错误信息格式与 OpenAI 不同 |
| OpenAI | `https://api.openai.com/v1` | 留空，提示选择支持工具调用的模型 | 本机网络可以访问 |
| 自定义 | 用户填写 | 用户填写 | 任何兼容 OpenAI 格式的服务 |

程序把“服务地址 + `/chat/completions`”作为请求网址。模型名都不写死，只作为可修改的默认值（MODEL-02）。

**统一做法**：请求中不发送 `tool_choice`，让模型自己决定是否调用工具（各家默认即自动）。这样避开了 GLM 和通义千问的限制，也意味着程序不能假设模型一定会调用工具：模型只回了文字，就当作“回答”处理。

### 10.2 给模型的两个工具

| 工具 | 用途 | 参数 |
|---|---|---|
| `propose_design_changes` | 提出设计修改 | `summary`：一句话说明；`ops`：修改指令列表（第 7.1 节） |
| `view_action` | 视图操作，不改设计 | `action`：聚焦房间、俯视、恢复视角、高亮对象、切换页面、切换剖面；`target`：对象编号 |

回答类问题直接回复文字，不用工具。这对应需求 7.1 的三类输出。

工具参数说明由 Zod 定义自动生成，但给模型的版本适度简化（把指令写成“`op` + 目标 + 字段对象”的扁平结构），因为层层嵌套的复杂结构在部分厂商可能不被严格遵守。严格检查始终由引擎完成，模型写错只会被拒绝并收到错误说明，不会造成错误修改。

### 10.3 每轮发送的内容（AI-02、AI-09）

| 位置 | 内容 |
|---|---|
| 系统消息 | 角色与规则（只能用工具改设计、不明确先问、不能声称已应用）；第 5 节坐标定义原文；指令说明与例子；家具模板目录；风格预设；**本轮最新的设计快照**；当前选中对象、页面、模式、是否在试看中；上一份试看的处理结果（已应用、已放弃或已过期） |
| 历史对话 | 最近 10 轮（每轮 = 用户消息 + 助手回复 + 工具调用和工具结果），并限制总字数约 2.4 万字；超出时从最早一轮整轮删除 |
| 最后一条 | 用户本次输入 |

设计快照只放在本轮系统消息里，历史消息中不带旧快照，所以模型看到的设计永远是最新的一份。快照是精简 JSON：每个房间附上程序算好的室内净尺寸、相邻房间、墙段列表（编号、类型、厚度、长度、墙上门窗）；选中房间额外给出全部家具细节。按 12 个房间、120 件家具估算约 1.7 万字符，在各家常见模型可接收的长度之内（M4 实测确认）。

裁剪历史时遵守两条规则：工具调用和它的工具结果必须一起保留或一起删除；裁剪后的历史必须以用户消息开头。否则部分厂商会直接报错。此前水杯原型的问题之一，正是工具结果没有回传给模型。

**图片附件（AI-10～12，需求 v0.8）**：发送消息时可附带图片（户型图、家具或风格参考）。程序把图片压缩到长边 1600 像素以内，按各家格式编码后随该条用户消息发送；单轮最多 3 张，历史中最多保留最近 6 张，更早的替换为「[图片已省略]」占位，避免每轮重复上传大额计费内容。识别不新增工具：模型看图后照常调用 `propose_design_changes`，输出仍是第 7.1 节的指令——户型图产出房间与门窗的初稿、家具只能引用内置家具模板、风格只改风格参数；引擎照常整批检查，不合法照样拒绝并回传重试，用户始终先试看再应用。哪家服务的哪个模型接受图片输入在 M4 实测确认（MODEL-02），不预先写死；不支持的组合在选择附件时就提示，不发空请求。

### 10.4 一次对话的流程

```text
用户发送 ──▶ 组装请求 ──▶ 调用模型（60 秒超时，可取消）
                            │
          ┌─────────────────┼──────────────────────┐
       只回文字          view_action          propose_design_changes
          │                 │                         │
       显示回答        执行视图操作，             引擎试执行（基于当前设计；
                      回传“已执行”               若在“继续调整”，基于当前试看）
                                                       │
                                     ┌─────────────────┴────────────┐
                                  检查失败                        检查通过
                                     │                               │
                        把错误作为工具结果回传，             生成试看；对话中显示
                        自动重试，最多 2 次                  模型的说明 + 程序的差异列表
                                     │                     工具结果记为“已进入试看，等待用户”
                        仍失败：再请求一次，要求模型
                        向用户解释原因，不再提交修改
```

- 一次用户发送最多调用模型 4 次，防止循环。等待期间发送按钮不可用，可点“停止”（AI-01）。
- 一次回复里有多份修改提议时，只采用第一份，其余回传“一次只能提交一份修改”。
- **试看成功后不再额外调用模型**：差异列表由程序生成，准确且即时。用户点应用或放弃后，对话中出现一条程序生成的状态，例如“已应用：改动 3 处”；下一轮请求中把这个结果告诉模型（第 17 节第 1 条）。
- **等待期间设计变了**：模型的建议基于旧版本，按第 8.3 节的冲突规则判断，冲突时不生成试看，提示“设计在等待期间已变化”，提供“重新生成”（AI-07）。
- 温度设为 0.3，减少随意发挥；首版不使用流式输出，结果一次到齐（TRY-01 本来也要求整组生成完再显示）。

### 10.5 错误说明（MODEL-04）

| 情况 | 判断依据 | 显示给用户 |
|---|---|---|
| 缺密钥 | 发送前检查 | 请先在设置中填写 API Key |
| 鉴权失败 | 状态码 401、403 | 密钥无效或已过期，请检查 |
| 模型不存在 | 404，或错误码含 `model_not_found` | 模型名称不对，请到厂商控制台核对 |
| 不支持所需能力 | 400 且错误信息提到 tools 或 function | 该模型不支持工具调用，请换一个模型 |
| 不支持图片 | 400 且错误信息提到 image、multimodal 或 vision | 该模型不支持图片输入，请换支持视觉的模型，或去掉图片再发 |
| 额度或频率 | 429；错误码含 `insufficient_quota` 时为额度不足 | 额度不足 / 请求太频繁，请稍后再试 |
| 服务异常 | 5xx | 服务暂时不可用 |
| 超时 | 60 秒到时自动取消 | 等待超时，可重试 |
| 网络或跨域 | 请求直接失败，无状态码 | 网络不通或被拦截，请检查网络 |

错误内容统一按“`error.message` → `message` → 原始文本”的顺序读取，兼容 GLM 的格式。任何错误都不影响当前设计。

**测试连接**（MODEL-03）：只在点击时发送一个最小请求（带一个空工具、最多返回 16 个词元），能确认地址、密钥、模型名和“接受工具参数”这几项；不能证明模型会正确使用工具，这一点在 M4 用固定样例实测。

## 11. 平面页

### 11.1 绘制内容

平面图用 SVG 绘制，坐标单位直接用毫米，缩放平移只改变“视窗”，不改数据（需求 4.1）。从下到上依次画：网格 → 房间底色 → 墙（按真实厚度画成粗线段）→ 门窗（门洞缺口、平开门画开启弧线、移门画滑动箭头、窗画三条细线）→ 家具（模板符号 + 正面标记）→ 名称和尺寸标注 → 选中框、控制点、对齐参考线。

- 房间标注“名称 + 轴线尺寸”，如“客厅 5.00 × 4.00 m（轴线）”；房间在屏幕上小于约 60 像素时只显示名称或不显示，避免文字盖住房间（ROOM-07）。
- 房间维度下，家具变淡且点不中；家具维度下，房间和墙点不中，点空白处取消选中（PAGE-04）。
- 选中墙段时，在参考端画一个圆点和指向另一端的箭头，门窗“位置”从这个圆点量起（DOOR-02）。
- 角落显示比例尺；提供“适合窗口”按钮。

### 11.2 编辑操作（编辑模式）

| 操作 | 方式 | 提交时机 |
|---|---|---|
| 新建房间 | 工具栏“画房间”，在画布拖出矩形 | 松手 |
| 移动、改大小 | 拖动房间内部移动；拖 8 个控制点改长宽 | 松手 |
| 选墙、加门窗 | 点墙段选中，面板里“在此墙添加门/窗”；拖动门窗沿墙移动 | 松手 |
| 家具 | 从面板选模板后点房间放置；拖动移动；控制点改大小；旋转手柄转向，每 15° 吸附 | 松手 |
| 复制、删除 | Cmd/Ctrl+D 复制（放到不重叠的位置），Delete 删除（删房间时先确认，EDIT-05） | 立即 |
| 微调 | 方向键 10 mm，按住 Shift 为 100 mm | 立即，合并为一步 |
| 撤销、重做 | Cmd/Ctrl+Z，Shift+Cmd/Ctrl+Z | — |

吸附：网格 100 mm（可选 50、100、500），离其他房间的边 8 像素以内时吸附并显示对齐参考线；按住 Alt（Option）临时关闭吸附（ROOM-05）。

拖动过程中每一帧都用引擎做一次“试执行”，不合法时对象显示红色轮廓和原因，但不提交；松手时若仍不合法，退回拖动前的位置并保留提示。

### 11.3 参数面板

- 显示选中对象的名称、类型和可改项目；没有选中时显示操作提示（EDIT-01）。
- 输入回车或离开输入框时提交；不合法时输入框标红、显示原因，数据保持原值，不偷偷改成别的数（EDIT-04）。
- 房间面板显示只读的“室内净尺寸（参考）”和方向示意图（ROOM-02）。
- 墙面板显示“客厅侧”“卧室侧”两个颜色（WALL-03），以及所属房间和范围（只读）。
- 门窗面板随类型显示适用的字段：无门扇的门不显示门扇颜色和开向。
- 删除房间的确认框写明影响，例如“将同时删除：家具 4 件、门窗 2 个；与卧室之间那扇门将改由卧室持有并保留”。

### 11.4 预览模式与试看显示

- 预览模式：可以缩放、平移、点选查看，面板只读，没有控制点。
- 试看与历史查看：顶部横幅“试看中，尚未应用”或“正在查看历史版本，尚未恢复”；改动的对象用虚线高亮，旧位置画淡色轮廓（TRY-02）。

## 12. 3D 页

### 12.1 场景怎么生成

3D 场景是“显示用设计”的纯函数：同一份设计必然生成同一个场景。设计变化后，只重建变化了的房间、墙段和家具（借助 Immer，没变的对象引用不变，比较引用就能知道），并及时释放旧模型占用的显存。

- **地面**：每个房间一块薄板，按房间轴线矩形铺，厚 30 mm；开放连接的两间地面直接相接（WALL-04）。
- **墙**：每段墙是一个长方体，按门窗位置切开：洞口两侧是墙块，门洞上方有过梁块，窗洞下方有窗台块，洞口自然形成，不是贴图（需求 5.3）。转角处竖直墙让位给水平墙，避免两块重叠闪烁。
- **门窗**：门框、门扇按开启方式生成，平开门在微开状态下显示开向；窗为窗框 + 半透明玻璃。
- **家具**：调用模板的造型函数，用圆角方块等基本体拼成。

### 12.2 展示基座与单间展台（VIEW-07、需求 8.1、8.3）

- **全屋大基座**：一个圆角长方体，水平范围 = 房屋外轮廓（含外墙厚度）四周再加 600 mm 边距；顶面紧贴地板下方，高度 450 mm。房屋变大变小，基座自动跟着变。
- **单间视图**：只显示这一间的地面、四周墙段（共用墙也显示，朝本房间一面用本房间颜色，另一面用中性色）、墙上门窗（包括相邻房间持有的）和家具，放在按本房间外轮廓加 300 mm 边距生成的小展台上；默认开启剖面。
- 单间视图提供房间下拉列表和“上一间／下一间”，以及“回到全屋”。在单间视图中修改，改的仍是同一份设计。

### 12.3 剖面（VIEW-03）

开启剖面时，朝向镜头一侧的墙段降到 1000 mm 高，墙块、过梁和窗按降低后的高度**重新生成**：门洞照样是缺口，高于剖切线的窗不显示，因此不会出现门窗悬空。转动镜头时，只在“朝向镜头的墙段”发生变化时重建，不是每帧都重建。

### 12.4 镜头与灯光

- 透视相机，视角约 35°，默认从斜上方约 40° 俯看，有微缩模型的感觉。
- 轨道操作：拖动旋转、滚轮缩放、右键平移；限制俯仰角（10°–85°）不钻到地下；有轻微惯性。提供“恢复视角”和“俯视”按钮（VIEW-01）。
- 自动取景只在这些时刻发生：首次进入 3D、进入或切换单间、房屋外轮廓明显变化（超过 20%）、点“恢复视角”。取景范围包含基座，但以房屋为主；平时不抢回用户的视角（VIEW-05）。
- 灯光：一盏环境光（天空/地面两色）+ 一盏带柔和阴影的平行光；灯光颜色由风格色温换算，亮度由风格控制；使用电影感色调映射，画面柔和不刺眼。

### 12.5 点选与编辑（PAGE-02）

- 点击时用射线检测找到被点中的对象；每个模型都标记了对象类型和编号。
- 房间维度只能点中地面、墙和门窗；家具维度只能点中家具。点中后与平面页共享选中状态，右侧用同一个参数面板修改。
- 首版不在 3D 中拖动（需求第 2 节已确定）。

### 12.6 试看显示与出错处理

- 试看时 3D 顶部有“修改前／修改后”切换；“修改后”中改动过的对象加一圈高亮描边（TRY-02）。
- 打开 3D 页前检查浏览器是否支持 WebGL2。不支持或加载失败时，显示原因和“切换到平面图”按钮，平面图照常可用（VIEW-06）。

## 13. 性能目标

需求要求“在方案阶段确定指标”。以下为目标值，在 M3 结束时实测，结果写入验收清单；达不到时先优化，再与用户商量是否调整。

| 项目 | 目标 |
|---|---|
| 测试规模 | 12 个房间、120 件家具、30 个门窗 |
| 测试电脑 | 用户当前使用的 Mac，Chrome 最新版 |
| 平面拖动 | 拖动时画面跟手，每次更新不超过 50 毫秒 |
| 提交后 3D 更新 | 不超过 300 毫秒 |
| 3D 旋转 | 不低于每秒 30 帧 |
| 打开程序到可编辑 | 不超过 3 秒 |

## 15. 里程碑

与需求 12.1 的开发顺序一致。每一步都要能实际打开操作，并有明确的完成标准。

## 16. 风险与预案

| 风险 | 影响 | 预案 |
|---|---|---|
| 厂商收紧跨域限制 | 浏览器无法直连 | 在 `serve.mjs` 中增加一个默认关闭的转发开关（约 50 行），请求经本机转发；密钥仍只在本机 |
| 模型算错数、编错指令 | 修改不符合预期 | 提供增量写法 `add`；上下文给出程序算好的净尺寸和墙段；引擎严格检查并把错误回传重试；试看让用户先看再应用 |
| 视觉识别不准（户型图估错尺寸、家具映射不合适） | 识别结果误导用户 | 识别输出仍是普通指令，由引擎照常拦截不合法项；一律先试看再应用；提示写明“识别初稿，请核对” |
| 不同模型调用工具的稳定性不同 | 部分模型只回文字不改设计 | 不强制工具调用；M4 用固定样例记录各家表现，在设置里标注推荐模型 |
| 设计很大时上下文过长 | 请求变慢或超出模型上限 | 精简 JSON，只对选中房间给完整细节；历史对话限额 |
| 浏览器清理本地数据 | 设计丢失 | 申请持久存储；界面提醒定期导出；保存失败立刻提示 |
| 3D 性能不达标 | 卡顿 | 只重建变化对象、共用材质、控制阴影范围；必要时降低阴影质量 |
| 工具链版本变化 | 安装或构建失败 | 用 `package-lock.json` 锁定版本；TypeScript 暂用 6.0.3 |
| 另一台电脑没有 Node | 程序无法启动 | 使用说明给出 Node 官网下载步骤；Python 自带的静态服务可作为应急方案，但需固定同一端口 |

## 17. 与需求的差异和补充

以下内容与需求原文略有出入或是需求未写到的细节，评审时请重点看第 1 条。

| 编号 | 内容 | 原因 |
|---|---|---|
| 1 | **试看后的结果说明**：需求 7.1 第 6 步写“由 AI 说明已应用、已放弃……”。方案改为：应用、放弃、过期的结果由程序直接在对话中显示一条确定的状态，下一轮再把结果告诉模型，不为此单独调用一次模型 | 程序的说明一定准确、即时、不耗额度，更好地满足 AI-05“不能声称已修改”；代价是这一步没有 AI 的口语化总结 |
| 2 | 家具拖动旋转每 15° 吸附，参数面板可输入任意整数角度 | 拖动时便于对齐，又不限制精确输入 |
| 3 | 共用墙的厚度、高度、开放按“房间对”保存；两间房不再相邻时这些设置被移除，并在差异列表中说明 | 墙段由房间推导，没有不依赖房间的独立身份 |
| 4 | 删除房间时，该房间持有的、位于共用墙上的门窗改由相邻房间持有并保留；只在被删房间外墙上的门窗随房间删除。确认框中列出 | 共用墙仍在（需求 4.2），墙上的门不应无故消失 |
| 5 | 家具必须在所属房间的室内范围内，即使两间房之间开放，也不能横跨两间 | 每件家具只能属于一个房间，否则归属和检查都会含糊 |
| 6 | 外墙朝外一面的颜色跟随风格墙面色，首版不单独编辑 | 需求只要求区分共用墙两侧；保持面板简单 |
| 7 | 首批家具在需求建议的 9 种之外补充“地毯” | 用于体现“可叠放家具不提示重叠”的规则 |
| 8 | 新增全局默认墙厚（外墙 240、共用墙 120）和默认墙高 2800，可在设置中修改 | 不必逐面墙填写 |
| 9 | 对话记忆具体为最近 10 轮、约 2.4 万字 | 落实 AI-09“数量在方案阶段确定” |
| 10 | 程序固定使用 `http://127.0.0.1:5180` | 浏览器本地数据与网址绑定，换端口会“看不到”之前的设计 |
